# تمرین Git

## سؤال ۱: merge و rebase

هر دو دستور برای ترکیب تغییرات شاخه‌ها استفاده می‌شن، ولی شکل تاریخچه‌ای که می‌سازن فرق داره.

با <code dir="ltr">git merge</code>، تغییرات یک شاخه وارد شاخه‌ای می‌شه که الان روش هستیم. اگر دو شاخه از هم جدا شده باشن و هر دو کامیت جدید داشته باشن، Git معمولاً یک merge commit می‌سازه که دو والد داره. کامیت‌های قبلی عوض نمی‌شن و مسیر جدا شدن و دوباره به هم رسیدن شاخه‌ها توی تاریخچه می‌مونه. اگر شاخهٔ فعلی فقط عقب‌تر باشه، merge می‌تونه به صورت fast-forward انجام بشه؛ یعنی اشاره‌گر شاخه جلو بره و کامیت جدیدی ساخته نشه.

مثلاً برای وارد کردن یک قابلیت تکمیل‌شده به <code dir="ltr">main</code> می‌زنم:

<div dir="ltr" align="left">

```bash
git switch main
git merge feature-description
```

</div>

برای شاخه‌ای که چند نفر روش کار کردن، merge رو انتخاب می‌کنم چون کامیت‌های قبلی رو بازنویسی نمی‌کنه و تاریخچهٔ کار گروهی حفظ می‌شه.

با <code dir="ltr">git rebase</code>، کامیت‌های مخصوص شاخهٔ فعلی دوباره روی انتهای شاخهٔ مقصد اعمال می‌شن. در حالت معمول، این کامیت‌ها شناسه‌های جدید می‌گیرن چون والدشون عوض شده. نتیجه اینه که تاریخچه خطی‌تر می‌شه و انگار کار روی شاخهٔ جدید از آخرین وضعیت شاخهٔ مقصد شروع شده.

مثلاً وقتی روی یک شاخهٔ شخصی کار می‌کنم و هنوز کامیت‌هام رو با کسی به اشتراک نذاشتم، برای هماهنگ شدن با تغییرات جدید <code dir="ltr">main</code> می‌زنم:

<div dir="ltr" align="left">

```bash
git switch feature-description
git rebase main
```

</div>

اینجا rebase مناسبه چون قبل از ادغام، تغییرات خودم روی نسخهٔ جدید <code dir="ltr">main</code> قرار می‌گیرن و تاریخچه هم مرتب‌تر می‌شه. روی کامیت‌هایی که بقیه دریافت کردن، بدون هماهنگی rebase نمی‌کنم چون بازنویسی تاریخچه می‌تونه کارشون رو به مشکل بندازه. در هر دو روش هم اگر تغییرات ناسازگار باشن، ممکنه conflict پیش بیاد.

## سؤال ۲: انتخاب بخشی از تغییرات

یک <code dir="ltr">hunk</code> یعنی یک بخش از خروجی diff که چند خط تغییرکردهٔ نزدیک به هم و معمولاً چند خط اطرافشون رو نشون می‌ده. لازم نیست هر hunk دقیقاً یک تغییر منطقی باشه؛ ممکنه دو تغییر متفاوت چون نزدیک هم هستن توی یک hunk قرار بگیرن. ابتدای این بخش معمولاً خطی با علامت <code dir="ltr">@@</code> دیده می‌شه که محدودهٔ خط‌ها رو مشخص می‌کنه.

برای بررسی تغییرات یک فایل و انتخاب بخشی از اون‌ها می‌زنم:

<div dir="ltr" align="left">

```bash
git diff -- README.md
git add -p -- README.md
```

</div>

دستور اول تغییرات واردنشده به staging رو نشون می‌ده. دستور دوم همین تغییرات رو بخش‌به‌بخش نمایش می‌ده و برای هر بخش ازم می‌پرسه که وارد staging بشه یا نه. انتخاب‌های اصلی این‌ها هستن:

- <code dir="ltr">y</code>: همین بخش وارد staging بشه.
- <code dir="ltr">n</code>: این بخش وارد staging نشه و بررسی ادامه پیدا کنه.
- <code dir="ltr">s</code>: اگر امکانش باشه، بخش فعلی به بخش‌های کوچک‌تر تقسیم بشه.
- <code dir="ltr">e</code>: patch رو دستی ویرایش کنم تا فقط قسمت موردنظر وارد staging بشه؛ این کار خود فایل رو ویرایش نمی‌کنه.
- <code dir="ltr">q</code>: از بررسی خارج بشم؛ بخش‌هایی که تا اینجا انتخاب کردم توی staging می‌مونن.
- <code dir="ltr">?</code>: راهنمای انتخاب‌ها رو ببینم.

بعد از انتخاب، نتیجه رو بررسی و کامیت می‌کنم:

<div dir="ltr" align="left">

```bash
git diff --cached -- README.md
git diff -- README.md
git commit -m "Update project description"
```

</div>

دستور اول بخش آمادهٔ کامیت و دستور دوم تغییرات باقی‌مونده رو نشون می‌ده. کامیت معمولی فقط تغییرات staging رو ثبت می‌کنه. این روش کمک می‌کنه مثلاً اصلاح یک اشتباه و اضافه کردن یک توضیح جدید رو در دو کامیت جدا ثبت کنم. هر کامیت یک موضوع مشخص داره و بررسی یا برگردوندنش راحت‌تر می‌شه.

## سؤال ۳: یافتن منشأ خطا

<code dir="ltr">git bisect</code> با یک جست‌وجوی شبیه جست‌وجوی دودویی، اولین کامیتی رو پیدا می‌کنه که خطای موردنظر توش دیده می‌شه. یک کامیت سالم و یک کامیت خراب رو مشخص می‌کنم، بعد Git یک کامیت میانی رو برای آزمایش انتخاب می‌کنه. با مشخص کردن سالم یا خراب بودن هر مرحله، محدودهٔ جست‌وجو کوچک‌تر می‌شه.

مثلاً فرض می‌کنم ورود کاربر در نسخهٔ <code dir="ltr">v1.0</code> درست کار می‌کرده، ولی در آخرین کامیت خراب شده. قبل از شروع، تغییرات ثبت‌نشده رو کامیت یا stash می‌کنم تا جابه‌جایی بین نسخه‌ها مشکلی ایجاد نکنه. بعد می‌زنم:

<div dir="ltr" align="left">

```bash
git bisect start
git bisect bad HEAD
git bisect good v1.0
```

</div>

<code dir="ltr">HEAD</code> رو خراب و <code dir="ltr">v1.0</code> رو سالم معرفی کردم. حالا Git یک کامیت بین این دو رو checkout می‌کنه. برنامه رو در همون نسخه اجرا می‌کنم و دقیقاً همون مشکل ورود رو آزمایش می‌کنم. اگر ورود درست بود، می‌زنم:

<div dir="ltr" align="left">

```bash
git bisect good
```

</div>

اگر همون خطا وجود داشت، به جاش می‌زنم:

<div dir="ltr" align="left">

```bash
git bisect bad
```

</div>

این مراحل رو تکرار می‌کنم تا Git اولین کامیت خراب رو معرفی کنه. اگر یک نسخه به دلیل دیگری قابل آزمایش نبود، با <code dir="ltr">git bisect skip</code> ازش رد می‌شم؛ البته رد کردن بعضی نسخه‌ها ممکنه باعث بشه نتیجه به یک کامیت مشخص محدود نشه. در پایان می‌زنم:

<div dir="ltr" align="left">

```bash
git bisect reset
```

</div>

این دستور جست‌وجو رو تموم می‌کنه و به وضعیت قبل از شروع bisect برمی‌گردونه. بعد تغییرات کامیت پیدا‌شده رو بررسی می‌کنم تا علت خطا مشخص بشه.

فایده‌اش اینه که لازم نیست همهٔ کامیت‌ها رو یکی‌یکی آزمایش کنم. مثلاً بین حدود ۱۲۸ کامیت، معمولاً با حدود ۷ بار آزمایش می‌شه محدوده رو به یک کامیت رسوند. برای نتیجهٔ درست، باید یک خطای مشخص رو با آزمایش ثابت دنبال کنم و فرض این باشه که خطا بعد از ورودش تا نسخهٔ خراب موردنظر باقی مونده.

## سؤال ۴: بررسی تغییرات پیش از کامیت

### ۱. بررسی وضعیت و دو دستهٔ تغییرات

برای دیدن وضعیت مخزن و تغییرات <code dir="ltr">README.md</code> می‌زنم:

<div dir="ltr" align="left">

```bash
git status
git diff -- README.md
git diff --cached -- README.md
```

</div>

<code dir="ltr">git status</code> نشون می‌ده چه فایل‌هایی staged، unstaged یا untracked هستن. در این مثال، <code dir="ltr">README.md</code> می‌تونه هم در بخش تغییرات آمادهٔ کامیت و هم در بخش تغییرات واردنشده به staging دیده بشه؛ چون یک نسخه ازش رو stage کردم و بعد دوباره فایل رو تغییر دادم.

<code dir="ltr">git diff</code> نسخهٔ فعلی فایل در working tree رو با نسخهٔ staging مقایسه می‌کنه. پس هم تغییرات قبلی که انتخاب نکردم و هم ویرایش‌های بعد از staging رو نشون می‌ده. <code dir="ltr">git diff --cached</code> نسخهٔ staging رو با آخرین کامیت، یعنی <code dir="ltr">HEAD</code>، مقایسه می‌کنه و تغییرات آمادهٔ کامیت رو نشون می‌ده. فایل‌های untracked پوشهٔ <code dir="ltr">tmp/</code> در diff معمولی نمایش داده نمی‌شن، ولی در status دیده می‌شن.

### ۲. نتیجهٔ یک کامیت معمولی

اگر بدون <code dir="ltr">-a</code> و بدون دادن مسیر فایل، این دستور رو اجرا کنم:

<div dir="ltr" align="left">

```bash
git commit -m "Update README"
```

</div>

فقط نسخه‌ای از <code dir="ltr">README.md</code> که توی staging قرار داره ثبت می‌شه. تغییراتی که stage نکردم و ویرایش‌های بعدی در working tree باقی می‌مونن. فایل‌های untracked پوشهٔ <code dir="ltr">tmp/</code> هم وارد کامیت نمی‌شن. دلیلش اینه که کامیت معمولی از staging ساخته می‌شه، نه مستقیم از آخرین محتوای فایل‌ها در working tree.

### ۳. نادیده گرفتن فایل‌های موقت

در فایل <code dir="ltr">.gitignore</code> ریشهٔ مخزن، این خط رو اضافه می‌کنم:

<div dir="ltr" align="left">

```gitignore
/tmp/
```

</div>

این الگو پوشهٔ <code dir="ltr">tmp</code> در ریشهٔ مخزن و محتویاتش رو نادیده می‌گیره تا با دستورهای معمولی مثل <code dir="ltr">git add .</code> وارد staging نشن. خود <code dir="ltr">.gitignore</code> رو هم ثبت می‌کنم تا این تنظیم برای بقیهٔ اعضای مخزن وجود داشته باشه.

این تنظیم برای فایلی که از قبل tracked شده کافی نیست. اگر مثلاً <code dir="ltr">tmp/cache.txt</code> قبلاً ثبت شده باشه، برای خارج کردنش از پیگیری Git و نگه داشتن نسخهٔ محلی می‌زنم:

<div dir="ltr" align="left">

```bash
git rm --cached -- tmp/cache.txt
```

</div>

بعد این حذف از مخزن رو همراه تنظیم <code dir="ltr">.gitignore</code> کامیت می‌کنم. فایل از روی سیستم خودم پاک نمی‌شه، ولی دیگه در نسخه‌های بعدی مخزن پیگیری نمی‌شه. در خود سناریوی سؤال، چون همهٔ فایل‌های <code dir="ltr">tmp/</code> از اول untracked هستن، این مرحله لازم نیست.

## سؤال ۵: رفع merge conflict در کار گروهی

### ۱. دلیل conflict

هر دو نفر نسبت به کامیت مشترک، یک خط یکسان رو به دو متن متفاوت تغییر دادیم. Git نمی‌تونه خودش تصمیم بگیره کدوم متن در نتیجهٔ نهایی باشه، برای همین conflict گزارش می‌کنه.

صرفاً تغییر دادن یک فایل توسط دو نفر الزاماً conflict ایجاد نمی‌کنه. اگر تغییرات در بخش‌های جدا و بدون تداخل باشن، Git معمولاً خودش اون‌ها رو ترکیب می‌کنه.

### ۲. پیدا کردن فایل و دو نسخهٔ متن

با توجه به اینکه working tree تمیزه، برای ادغام شاخهٔ خودم در <code dir="ltr">main</code> می‌زنم:

<div dir="ltr" align="left">

```bash
git switch main
git merge feature-description
```

</div>

بعد از گزارش conflict، برای شناسایی فایل‌های درگیر از این دستورها استفاده می‌کنم:

<div dir="ltr" align="left">

```bash
git status
git diff --name-only --diff-filter=U
git diff -- README.md
```

</div>

<code dir="ltr">git status</code> فایل‌های حل‌نشده رو نشان می‌ده و دستور دوم فقط نام فایل‌های unmerged رو فهرست می‌کنه. فایل <code dir="ltr">README.md</code> رو هم باز می‌کنم. در حالت معمول، بخش ناسازگار شبیه اینه:

<div dir="ltr" align="left">

```text
<<<<<<< HEAD
This project contains the course exercises.
=======
This project includes examples of Git commands.
>>>>>>> feature-description
```

</div>

بین <code dir="ltr">&lt;&lt;&lt;&lt;&lt;&lt;&lt; HEAD</code> و <code dir="ltr">=======</code> متن شاخهٔ فعلی، یعنی <code dir="ltr">main</code>، قرار داره. بین <code dir="ltr">=======</code> و <code dir="ltr">&gt;&gt;&gt;&gt;&gt;&gt;&gt; feature-description</code> متن شاخه‌ایه که دارم واردش می‌کنم. این علامت‌ها مرز دو نسخه رو مشخص می‌کنن و نباید توی جواب نهایی فایل باقی بمونن.

### ۳. حفظ هر دو تغییر و تکمیل merge

چون اطلاعات هر دو متن باید حفظ بشه، قسمت ناسازگار رو دستی به یک متن ترکیبی تبدیل می‌کنم. مثلاً نتیجهٔ مثال بالا می‌تونه این باشه:

<div dir="ltr" align="left">

```text
This project contains the course exercises and examples of Git commands.
```

</div>

تمام علامت‌های conflict رو حذف می‌کنم و فایل رو ذخیره می‌کنم. بعد هم متن رو می‌خونم تا مطمئن بشم اطلاعات هر دو تغییر باقی مونده و برای بررسی علامت‌های جا‌مونده می‌زنم:

<div dir="ltr" align="left">

```bash
git diff --check
```

</div>

این دستور علاوه بر بعضی خطاهای فاصله‌گذاری، علامت‌های conflict باقی‌مونده رو هم گزارش می‌کنه. سپس نسخهٔ حل‌شده رو وارد staging می‌کنم و نتیجه رو دوباره بررسی می‌کنم:

<div dir="ltr" align="left">

```bash
git add -- README.md
git diff --cached --check
git diff --cached -- README.md
git status
```

</div>

با <code dir="ltr">git add</code> به Git اعلام می‌کنم که conflict این فایل حل شده. در diff آمادهٔ کامیت، متن نهایی رو بررسی می‌کنم و با status مطمئن می‌شم فایل حل‌نشده‌ای باقی نمونده. اگر فایل دیگری هم conflict داشته باشه، همین مراحل رو برای اون تکرار می‌کنم. در آخر merge رو تکمیل می‌کنم:

<div dir="ltr" align="left">

```bash
git commit -m "Merge feature-description into main"
git status
```

</div>

این کامیت، merge در حال انجام رو کامل می‌کنه و نتیجهٔ ترکیب دو شاخه رو ثبت می‌کنه. بعد از تکمیل، با فرض نداشتن تغییر دیگری، working tree دوباره تمیزه.

### ۴. لغو merge

اگر قبل از تکمیل merge تصمیم بگیرم فعلاً انجامش ندم، می‌زنم:

<div dir="ltr" align="left">

```bash
git merge --abort
```

</div>

با توجه به اینکه قبل از شروع، working tree تمیز بوده، به وضعیت قبل از merge برمی‌گردم. تغییرات ثبت‌شدهٔ هیچ‌کدوم از دو شاخه حذف نمی‌شن؛ فقط عملیات ادغام در حال انجام لغو می‌شه.

## سؤال ۶: انتخاب روش مناسب برای بازگرداندن تغییرات

### ۱. حذف تغییرات واردنشده به staging در notes.txt

برای کنار گذاشتن فقط تغییرات همین فایل می‌زنم:

<div dir="ltr" align="left">

```bash
git restore -- notes.txt
```

</div>

این دستور محتوای <code dir="ltr">notes.txt</code> در working tree رو از نسخهٔ staging برمی‌گردونه. طبق فرض سؤال، نسخهٔ staging با آخرین کامیت یکیه، پس فایل به همون نسخهٔ آخرین کامیت برمی‌گرده. staging و تاریخچه عوض نمی‌شن و فایل‌های دیگه هم دست‌نخورده می‌مونن. ویرایش‌های ثبت‌نشدهٔ این فایل از بین می‌رن، که در این موقعیت همون چیزیه که می‌خوام.

### ۲. خارج کردن فایل از staging و حفظ ویرایش‌ها

برای این حالت می‌زنم:

<div dir="ltr" align="left">

```bash
git restore --staged -- notes.txt
```

</div>

با گزینهٔ <code dir="ltr">--staged</code> فقط نسخهٔ staging این فایل به وضعیت <code dir="ltr">HEAD</code> برمی‌گرده. محتوای working tree تغییر نمی‌کنه، پس ویرایش‌هام باقی می‌مونن و به صورت unstaged دیده می‌شن. هیچ کامیتی ساخته یا حذف نمی‌شه. این روش مناسبه چون فقط آماده بودن تغییرات برای کامیت رو لغو می‌کنه.

### ۳. برگرداندن اثر کامیتی که روی main منتشر شده

اینجا از <code dir="ltr">git revert</code> استفاده می‌کنم. فرض می‌کنم شناسهٔ کامیت اشتباه <code dir="ltr">a1b2c3d</code> و نام remote برابر <code dir="ltr">origin</code> باشه:

<div dir="ltr" align="left">

```bash
git switch main
git pull --ff-only origin main
git revert a1b2c3d
git push origin main
```

</div>

اول <code dir="ltr">main</code> رو انتخاب و با نسخهٔ remote هماهنگ می‌کنم. گزینهٔ <code dir="ltr">--ff-only</code> باعث می‌شه اگر شاخه‌های محلی و remote از هم جدا شده باشن، pull متوقف بشه تا وضعیت رو بررسی کنم؛ در حالت معمول که <code dir="ltr">main</code> فقط عقب‌تره، شاخه جلو می‌ره.

<code dir="ltr">git revert</code> تغییرات معکوس کامیت مشخص‌شده رو اعمال می‌کنه و یک کامیت جدید برای ثبتش می‌سازه. چون کامیت موردنظر معمولیه و merge commit نیست، گزینهٔ انتخاب والد لازم ندارم. طبق فرض سؤال، conflict هم رخ نمی‌ده. بعد از تکمیل revert، working tree و staging با کامیت جدید هماهنگ هستن و، اگر تغییر دیگری نداشته باشم، تمیز می‌مونن. کامیت اشتباه همچنان در تاریخچه وجود داره، ولی اثرش با کامیت جدید برگردونده شده. در آخر با push، این اصلاح به مخزن مشترک می‌رسه.

حذف کامیت از تاریخچه و force push رو انتخاب نمی‌کنم چون بقیه قبلاً اون تاریخچه رو دریافت کردن و ممکنه بر اساسش کامیت جدید ساخته باشن. بازنویسی شاخهٔ مشترک باعث اختلاف تاریخچهٔ اعضای تیم می‌شه و حتی می‌تونه کامیت‌های اون‌ها رو از شاخهٔ remote کنار بزنه. revert تاریخچه رو حفظ می‌کنه و اصلاح رو به صورت یک تغییر جدید و قابل پیگیری ثبت می‌کنه.
