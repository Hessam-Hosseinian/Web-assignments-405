# تمرین عملی HTTP: احراز هویت با پراکسی

در این پروژه، سرویس قدیمی <code dir="ltr">go-httpbin</code> فقط داخل یک شبکهٔ خصوصی Docker اجرا می‌شود. تنها پراکسی روی پورت ۸۰ میزبان منتشر شده و پیش از فرستادن هر درخواست به سرویس داخلی، توکن JWT را بررسی می‌کند.

## سؤال ۱: اجرای سرویس فقط روی شبکهٔ داخلی

برای داخلی نگه داشتن یک سرویس باید هم آدرس شنود برنامه و هم مسیر دسترسی شبکه محدود شود. اگر سرویس و مصرف‌کننده روی یک ماشین باشند، برنامه می‌تواند فقط روی <code dir="ltr">127.0.0.1</code> گوش دهد؛ در این حالت درخواست‌هایی که از کارت شبکه می‌رسند به آن دسترسی ندارند. اگر چند ماشین داخل یک شبکه از سرویس استفاده می‌کنند، برنامه روی IP خصوصی مثل <code dir="ltr">10.x.x.x</code> یا <code dir="ltr">192.168.x.x</code> bind می‌شود و فایروال فقط ترافیک همان subnet یا میزبان‌های مشخص را مجاز می‌کند.

در محیط کانتینری هم نباید پورت سرویس داخلی را با <code dir="ltr">ports</code> روی میزبان publish کرد. در فایل <code dir="ltr">compose.yaml</code> این پروژه، کانتینر <code dir="ltr">legacy</code> فقط عضو شبکهٔ <code dir="ltr">private</code> است و این شبکه با گزینهٔ <code dir="ltr">internal: true</code> ساخته می‌شود. این کانتینر فقط پورت ۸۰۸۰ را داخل شبکهٔ Docker در اختیار پراکسی می‌گذارد و هیچ مسیر مستقیمی از میزبان یا اینترنت به آن وجود ندارد. پراکسی هم‌زمان عضو شبکهٔ خصوصی و شبکهٔ ورودی است و تنها پورت عمومی پروژه، پورت ۸۰ آن است.

این محدودسازی شبکه جای احراز هویت را نمی‌گیرد؛ بلکه باعث می‌شود حتی اگر تنظیمات سرویس قدیمی ناامن بود، مهاجم نتواند پراکسی را دور بزند و مستقیماً به سرویس وصل شود.

## سؤال ۲: فلسفهٔ TLS Termination

در TLS termination، اتصال HTTPS کاربر در پراکسی معکوس پایان پیدا می‌کند. پراکسی گواهی و کلید خصوصی را نگه می‌دارد، handshake و رمزگشایی را انجام می‌دهد و بعد درخواست HTTP معمولی را در شبکهٔ داخلی برای سرویس قدیمی می‌فرستد. بنابراین می‌توان بدون تغییر کد سرویسی که TLS را پشتیبانی نمی‌کند، ارتباط کاربران تا نقطهٔ ورودی شبکه را رمزنگاری و هویت دامنه را با گواهی معتبر تأیید کرد.

متمرکز شدن TLS در پراکسی چند مزیت دارد: نصب و تمدید گواهی‌ها در یک نقطه انجام می‌شود، الگوریتم‌ها و نسخه‌های TLS ضعیف یک‌جا غیرفعال می‌شوند و سربار رمزنگاری از سرویس‌های داخلی برداشته می‌شود. همین پراکسی می‌تواند در کنار TLS، کارهایی مثل احراز هویت، rate limiting، ثبت لاگ و مسیریابی را هم انجام دهد.

البته بعد از termination، مسیر پراکسی تا backend به طور پیش‌فرض رمزنگاری‌شده نیست. این روش وقتی قابل‌قبول است که شبکهٔ داخلی واقعاً ایزوله و قابل‌اعتماد باشد. اگر شبکهٔ داخلی مشترک یا نامطمئن باشد، باید از TLS دوباره بین پراکسی و backend یا <code dir="ltr">mTLS</code> استفاده کرد. همچنین TLS به تنهایی مجوز دسترسی کاربر را مشخص نمی‌کند؛ به همین دلیل این پروژه علاوه بر TLS termination پیشنهادی، احراز هویت JWT را در خود پراکسی پیاده‌سازی می‌کند.

## سؤال ۳: پیاده‌سازی JWT authentication proxy

پراکسی با زبان Go نوشته شده و دو endpoint عمومی دارد:

- <code dir="ltr">POST /auth/token</code>: نام کاربری و رمز عبور را با Basic Authentication می‌گیرد و یک JWT با عمر ۱۵ دقیقه می‌سازد.
- <code dir="ltr">GET /healthz</code>: سلامت خود پراکسی را گزارش می‌کند.

تمام مسیرهای دیگر به توکن <code dir="ltr">Bearer</code> نیاز دارند. پراکسی امضای <code dir="ltr">HS256</code>، زمان انقضا، صادرکننده و audience توکن را بررسی می‌کند. پس از تأیید، هدر حاوی JWT حذف می‌شود تا secret دسترسی کاربر بی‌دلیل به سرویس قدیمی نرسد؛ سپس نام کاربر در هدر <code dir="ltr">X-Authenticated-User</code> قرار می‌گیرد و درخواست به <code dir="ltr">http://legacy:8080</code> فرستاده می‌شود.

### ساختار پروژه

<div dir="ltr" align="left">

```text
.
├── compose.yaml       # شبکه‌ها و اجرای proxy و go-httpbin
├── Dockerfile         # ساخت image کوچک و اجرای non-root
├── main.go            # صدور/اعتبارسنجی JWT و reverse proxy
├── main_test.go       # آزمون‌های احراز هویت و عبور درخواست
├── go.mod
├── go.sum
├── vendor/            # وابستگی JWT برای build آفلاین و قابل‌تکرار
└── .env.example       # نمونهٔ متغیرهای لازم
```

</div>

### اجرا

ابتدا فایل تنظیمات محلی ساخته می‌شود. مقدار <code dir="ltr">JWT_SECRET</code> باید حداقل ۳۲ کاراکتر و غیرقابل‌حدس باشد و فایل <code dir="ltr">.env</code> نیز در Git ثبت نمی‌شود.

<div dir="ltr" align="left">

```bash
cp .env.example .env
openssl rand -hex 32
# مقدار تولیدشده و نام کاربری/رمز عبور دلخواه را در .env قرار دهید.
docker compose up --build -d
```

</div>

برای گرفتن توکن، نام کاربری و رمز عبور موجود در <code dir="ltr">.env</code> فرستاده می‌شود:

<div dir="ltr" align="left">

```bash
curl -u admin:YOUR_PASSWORD -X POST http://localhost/auth/token
```

</div>

مقدار <code dir="ltr">access_token</code> پاسخ را می‌توان برای دسترسی به سرویس داخلی استفاده کرد:

<div dir="ltr" align="left">

```bash
curl -i http://localhost/get \
  -H "Authorization: Bearer YOUR_ACCESS_TOKEN"
```

</div>

درخواست بدون توکن یا با توکن نامعتبر پاسخ <code dir="ltr">401 Unauthorized</code> می‌گیرد. در مقابل، درخواست معتبر توسط <code dir="ltr">go-httpbin</code> پاسخ داده می‌شود. برای توقف پروژه هم دستور زیر اجرا می‌شود:

<div dir="ltr" align="left">

```bash
docker compose down
```

</div>

### آزمون‌ها

آزمون‌ها بررسی می‌کنند که درخواست بدون توکن رد شود، اطلاعات ورود اشتباه توکن نگیرد، توکن امضاشده با secret دیگر معتبر نباشد و درخواست معتبر به backend برسد. همچنین بررسی می‌شود که پراکسی هدر JWT را به سرویس قدیمی نفرستد.

<div dir="ltr" align="left">

```bash
go test ./...
```
