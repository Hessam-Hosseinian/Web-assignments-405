# تمرین HTTP

## سؤال ۱: تفاوت نسخه‌های HTTP و استفاده از UDP در HTTP/3

نسخه‌های مختلف HTTP در طول زمان برای رفع محدودیت‌های نسخه‌های قبلی تغییر کردن.

<code dir="ltr">HTTP/0.9</code> خیلی ساده بود و فقط از متد <code dir="ltr">GET</code> پشتیبانی می‌کرد؛ پاسخ هم فقط شامل یک متن HTML بود و خبری از هدر یا کد وضعیت نبود.

در <code dir="ltr">HTTP/1.0</code> هدرها و متدهای بیشتری اضافه شدن، ولی برای هر درخواست یک اتصال TCP جدید باز و بسته می‌شد که سربار زیادی داشت.

در <code dir="ltr">HTTP/1.1</code> قابلیت استفادهٔ مجدد از اتصال (<code dir="ltr">Keep-Alive</code>) و <code dir="ltr">Pipelining</code> معرفی شد تا بشه چند درخواست رو پشت سر هم فرستاد، ولی همچنان مشکل <code dir="ltr">Head-of-Line Blocking</code> در سطح HTTP وجود داشت.

<code dir="ltr">HTTP/2</code> برای سرعت بیشتر روی یک اتصال TCP واحد، مالتی‌پلکسینگ (<code dir="ltr">Multiplexing</code>) و فشرده‌سازی هدرها (<code dir="ltr">HPACK</code>) رو آورد. اینجا مشکل اصلی، مسدود شدن کل اتصال به خاطر گم شدن یک بسته در سطح TCP بود.

<code dir="ltr">HTTP/3</code> برای حل همین مشکل، پروتکل انتقال رو به <code dir="ltr">QUIC</code> تغییر داد.

**چرا HTTP/3 از UDP استفاده می‌کند؟**
در TCP، به خاطر ماهیت ترتیبی و تضمین تحویل، اگر یک بسته گم بشه، بقیهٔ جریان‌ها هم باید منتظر بمونن تا اون بسته دوباره ارسال بشه (<code dir="ltr">Head-of-Line Blocking</code>). <code dir="ltr">QUIC</code> روی <code dir="ltr">UDP</code> ساخته شده تا کنترل ازدحام و تضمین تحویل رو در لایهٔ کاربرد پیاده‌سازی کنه. اینطوری اگه بسته‌ای در یک جریان گم بشه، بقیهٔ جریان‌ها بدون معطلی به کارشون ادامه می‌دن. علاوه بر این، UDP اجازه می‌ده اتصال سریع‌تر (<code dir="ltr">0-RTT</code> یا <code dir="ltr">1-RTT</code>) برقرار بشه و امنیت TLS هم به صورت توکار درش قرار بگیره.

## سؤال ۲: Stateful در برابر Stateless

### ۱. توضیح مختصر

<code dir="ltr">Stateless</code> (بدون حالت): سرور هیچ اطلاعاتی از درخواست‌های قبلی کلاینت نگه نمی‌داره. هر درخواست کاملاً مستقل بررسی می‌شه و کلاینت باید هر بار اطلاعات لازم (مثل توکن لاگین) رو بفرسته. مقیاس‌پذیریش خیلی بالاست چون هر سروری می‌تونه به هر درخواستی جواب بده.

<code dir="ltr">Stateful</code> (با حالت): سرور وضعیت کلاینت (مثل سبد خرید یا نشست لاگین) رو توی حافظه یا دیتابیس ذخیره می‌کنه. درخواست‌های بعدی به همون وضعیت وابسته‌ن. مدیریتش سخت‌تره و اگه چند سرور داشته باشیم، باید وضعیت رو بینشون به اشتراک بذاریم.

### ۲. جایگاه HTTP و راهکار

پروتکل HTTP ذاتاً **Stateless** هست. این ماهیت باعث می‌شه اگه بخوایم کاربر لاگین‌شده بمونه، مجبور باشیم هر بار اطلاعاتش رو بفرستیم. برای حل این مشکل، معمولاً از **کوکی‌ها (Cookies)** و **توکن‌ها (مثل JWT)** استفاده می‌کنم. سرور یک توکن به کلاینت می‌ده و کلاینت توی هدر درخواست‌های بعدی اون رو می‌فرسته. اینطوری وضعیت نشست (Session) در سمت کلاینت نگه‌داری می‌شه یا سرور فقط یک شناسه (Session ID) رو توی دیتابیس چک می‌کنه، بدون اینکه خود پروتکل HTTP حالت‌دار بشه.

## سؤال ۳: محدودیت مدل Client/Server و وب‌هوک

### ۱. توضیح چالش

در مدل سنتی <code dir="ltr">Client/Server</code>، همیشه کلاینت شروع‌کنندهٔ درخواسته. این برای دریافت اطلاعات لحظه‌ای (<code dir="ltr">Real-time</code>) و رویدادمحور مثل وب‌هوک‌ها یا سیستم‌های <code dir="ltr">Alerting</code> یک چالش بزرگه؛ چون سرور نمی‌تونه بدون اینکه کلاینت درخواستی داده باشه، داده‌ای رو بهش پوش کنه. اگه کلاینت بخواد از یک رویداد باخبر بشه، باید مدام از سرور سؤال کنه (<code dir="ltr">Polling</code>) که منابع و پهنای باند رو هدر می‌ده.

### ۲. راهکارها

برای حل این مشکل از روش‌های زیر استفاده می‌کنم:

- <code dir="ltr">Long Polling</code>: کلاینت درخواست می‌فرسته و سرور اتصال رو تا زمانی که داده‌ای برای ارسال باشه باز نگه می‌داره. به محض وقوع رویداد، سرور جواب می‌ده و کلاینت دوباره درخواست جدید می‌فرسته.
- <code dir="ltr">WebSockets</code>: یک اتصال دوطرفه و دائمی (<code dir="ltr">Full-Duplex</code>) بین کلاینت و سرور برقرار می‌شه. بعد از <code dir="ltr">Handshake</code> اولیه، سرور می‌تونه هر لحظه داده‌ای رو به کلاینت بفرسته. این روش برای چت و اطلاع‌رسانی‌های لحظه‌ای عالیه.
- <code dir="ltr">Server-Sent Events (SSE)</code>: کلاینت یک اتصال یک‌طرفه باز می‌کنه و سرور جریانی از داده‌ها (<code dir="ltr">Event Stream</code>) رو به سمتش می‌فرسته. این روش برای سیستم‌های <code dir="ltr">Alerting</code> و اطلاع‌رسانی سبک و مناسبه.
- <code dir="ltr">Webhooks</code> (سمت سرور): برای ارتباط سرور با سرور، سرور مبدأ یک درخواست HTTP POST به یک URL مشخص در سرور مقصد ارسال می‌کنه تا رویداد رو اطلاع بده.

## سؤال ۴: اجزای URL

URL داده شده اینه: <code dir="ltr">ss://asghar:1234!!@ss.myproxy.com:1234#shadowSocks1</code>. اجزای اون رو اینطوری جدا می‌کنم:

- **Scheme (پروتکل):** <code dir="ltr">ss</code>
- **User Info (اطلاعات کاربر):**
  - **Username:** <code dir="ltr">asghar</code>
  - **Password:** <code dir="ltr">1234!!</code>
- **Host (میزبان):** <code dir="ltr">ss.myproxy.com</code>
- **Port (پورت):** <code dir="ltr">1234</code>
- **Fragment (قطعه):** <code dir="ltr">shadowSocks1</code>

## سؤال ۵: انتخاب کد وضعیت HTTP

برای هر سناریو، کد وضعیت مناسب رو با توجه به استانداردها انتخاب کردم:

۱. **دیتبایس وب‌سایت شما مشکل پیدا کرده و درخواست‌های لایه‌ای انجام نمی‌شوند:**
کد <code dir="ltr">503 Service Unavailable</code> رو انتخاب می‌کنم. این کد نشون می‌ده که سرور به طور موقت نمی‌تونه درخواست‌ها رو پردازش کنه (مثلاً به خاطر تعمیرات یا اضافه‌بار). معمولاً همراهش هدر <code dir="ltr">Retry-After</code> هم می‌فرستن.

۲. **نام‌کاربری وارد شده در سایت وجود ندارد و لاگین ناموفق است:**
کد <code dir="ltr">401 Unauthorized</code> مناسبه. این کد برای وقتیه که احراز هویت شکست می‌خوره یا اطلاعات لاگین غلط ارسال شده. (کد 403 برای وقتیه که هویت مشخصه ولی دسترسی ممنوعه).

۳. **وب‌سایت به دامنه دیگری منتقل شده است:**
کد <code dir="ltr">301 Moved Permanently</code> رو می‌زنم. این کد انتقال دائمی رو نشون می‌ده. مرورگر و موتورهای جستجو به صورت دائم به آدرس جدید هدایت می‌شن.

۴. **تعداد درخواست‌هایی که از طرف این کاربر ارسال شده از نرخ مجاز بیشتر است:**
کد <code dir="ltr">429 Too Many Requests</code> مخصوص همین حالته. کاربر به محدودیت نرخ (<code dir="ltr">Rate Limiting</code>) برخورد کرده و معمولاً با هدر <code dir="ltr">Retry-After</code> همراهه تا بگه کی دوباره تلاش کنه.

۵. **درخواست تمدید توکن (JWT) موفقیت‌آمیز بوده و توکن تمدید شده داخل هدر بازگردانده شده:**
کد <code dir="ltr">200 OK</code> استفاده می‌کنم. درخواست با موفقیت انجام شده و پاسخ شامل توکن جدید (معمولاً در هدر یا بدنه) هست.

۶. **کاربر از رنج IP ممنوعه برای دسترسی به سرویس است:**
کد <code dir="ltr">403 Forbidden</code> درسته. سرور درخواست رو فهمیده، هویت کاربر هم مشخصه، ولی به دلیل قوانین (مثلاً IP ممنوعه) اجازهٔ دسترسی بهش نمی‌ده.

## سؤال ۶: نوع پروکسی استفاده شده

۱. **استفاده از سرورهای داخلی دانشگاه بجای سرورهای مرکزی برای دریافت پکیج‌ها (مانند apt در اوبونتو):**
اینجا از **Reverse Proxy (پروکسی معکوس)** استفاده شده. سرور داخلی دانشگاه به عنوان یک آینه (Mirror) عمل می‌کنه. یعنی درخواست‌های کلاینت‌های داخلی رو دریافت می‌کنه و به نمایندگی از سرورهای اصلی بهشون جواب می‌ده (یا از کش خودش استفاده می‌کنه). کلاینت‌ها فقط آدرس سرور داخلی رو می‌شناسن.

۲. **تقسیم درخواست‌ها بر اساس مبدا جغرافیایی درخواست‌ها:**
اینجا از **Forward Proxy (پروکسی پیش‌رو) / Geo-Proxy** استفاده می‌شه. یک واسط بین کاربران و اینترنت قرار می‌گیره که بر اساس موقعیت جغرافیایی کاربر (آی‌پی) تصمیم می‌گیره درخواست رو به کدوم سرور (محلی یا بین‌المللی) بفرسته. این کار معمولاً توسط یک <code dir="ltr">Forward Proxy</code> یا لودبالانسر هوشمند انجام می‌شه.

۳. **اضافه کردن قابلیت احراز هویت برای یک سرویس بسیار قدیمی:**
اینجا هم **Reverse Proxy** استفاده می‌کنم. یک پروکسی معکوس (مثل <code dir="ltr">Nginx</code>) رو جلوی سرویس قدیمی قرار می‌دم. این پروکسی وظیفهٔ احراز هویت کاربران رو بر عهده می‌گیره و فقط اگه کاربر معتبر بود، درخواست رو به سرویس قدیمی پاس می‌ده. اینطوری بدون اینکه کد سرویس قدیمی رو تغییر بدم، براش لایهٔ امنیتی اضافه کردم.
